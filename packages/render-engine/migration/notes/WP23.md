## 翻译要点与偏差

- **异步**：凡是会调用模型、出图或运行 LangGraph 图的函数都改成 async：`Text2DiagramWorkflow.run/_run_pipeline` 及 7 个阶段方法、`build_design_expertise`、`_retrieve_*`、`IterativeRefinerWorkflow.run/prepare/run_prepared/_iteration_node/_ensure_llm`、`_prepare_iteration`、`_run_one_iteration`、`_propose_llm_edits`、`_rerender_iteration_image`、`_refresh_image_for_llm`、`_node_finalize`、`initialize_model`、`initialize_router_model`、`process_example`、`learn_from_user_edit`、`main`。调用顺序与 Python 相同。`_node_load_inputs`、`_apply_edit_batch`、`_mark_convergence` 等纯计算函数仍是同步的。
- **参数**：keyword-only 参数按声明顺序改为位置参数，例如 `Text2DiagramWorkflow(model, config, save_dir, canvas_library, mode, …, router_model, …)`，`router_model` 是第 16 个参数。`run(text, query, runtime_directives, save_dir, final_dir, design_expertise, diagram_type, content_area, locked_nodes)` 中，`save_dir` 不传（`undefined`）就用哨兵 `_DEFAULT_SAVE_DIR`；传 `null` 等于 Python 的 `None`，会用临时目录。
- **状态与 dataclass**：`WorkflowState` 基于 `py/pydantic.ts`，字段顺序和默认值与 Python 相同，`pythonName` 为 `evodesign.agentic_system.workflow.WorkflowState`。`_GenerationArtifacts` 等 6 个 dataclass 改成同名类，字段顺序相同。快照按字段比较，回放已经确认一致。`VerifierRefinerState.model_construct(...)` 用本地的 `_model_construct` 实现：不做校验，缺的字段用默认值。
- **LangGraph**：`StateGraph(VerifierRefinerState)` 对应 `PydanticStateGraph`。节点 `load_inputs/run_iteration/finalize`、`START` 上的条件边以及两条条件边都与 Python 相同。`partial(_node_finalize, vlm_model_name=…)` 改成闭包。`config={"recursion_limit": N}` 对应 `{ recursionLimit: N }`。`_after_iteration` 在 path 函数里改 `termination_reason`；这和 Python 一样作用在重新校验出来的副本上，所以不会写回状态。
- **浮点标记**：`initial_report` 和 `refined_manifest` 用 `pyJsonLoadsExact` 读入。回滚快照和锁定快照用 `_deepcopy_with_py_floats`，保留 `PY_FLOAT_MARKS`。`_manifest_fingerprint` 在 dumps 之前先经过 `_with_py_floats`；对于从带标记的 JSON 读入的 manifest，这样算出的哈希与 Python 相同，向量 25/25 一致。但第一期渲染引擎写出的 manifest 本身就没有浮点信息，所以端到端回放中仍有分歧（WP23-2）。
- **路径**：`Path(...)` 的拼接和 `parent` 按 POSIX pathlib 规则实现（`_path_str/_path_join/_path_parent`），不折叠 `..`。`os.path.join` 改用 `node:path` 的 `join`。`os.path.commonpath` 改用 `relative` 判断。
- **`tempfile.TemporaryDirectory(prefix="evodesign_")`**：改用本地的 `_TemporaryDirectory`，生成 8 位 `[a-z0-9_]` 随机后缀（与 Python 相同），使归一化规则 `evodesign_XXXXXXXX` 也能匹配。录制样例都保存中间结果，没有走到这条路径。
- **`main`**：
  - argparse 改为自写的小解析器，见文件头。帮助文本是简化版。
  - Python 测试会 monkeypatch 模块全局 `EXAMPLES_DIR`、`DEFAULT_TEST_DATASET`、`get_experiment_id`、`get_evodesign_output_dir`。TS 通过可替换的 `_globals` 对象读取这些名字，做法同 WP20 的 `_report_writer`。
  - `_write_failure_artifact` 的 `traceback`：对没有抛出过的异常（`VerificationQualityError`），只输出 `evodesign.agentic_system.main.VerificationQualityError: …\n` 一行，与 Python 逐字相同（`big_en_aes__refine` 的 failure.json 已核对）。对真正抛出的异常，按 Python 的格式列出 JS 调用栈，栈帧内容无法与 Python 相同。错误类型名用 `name`，模块前缀取类上的 `pythonModule`。
  - `runRecordedPipeline(input, {chatModelFactory, outputDir, datasetPath, argv, env, rendererUrl})` 的步骤：
    1. 在调用期间应用 `input.env`，并设置 `EXCALIDRAW_RENDER_URL=rendererUrl`；
    2. 移除 `settings._ENV_OVERRIDES` 中的变量和 `EVO_LLM_RUN_*`（录制环境里没有这些变量）；
    3. 重置 `ModelConfig`/`AppSettings` 单例（Python 每个样例在新进程中录制）；
    4. 调用 `set_chat_model_factory(chatModelFactory)`；
    5. 按 `record_runs.py worker()` 的顺序执行；
    6. 在 `finally` 中恢复上述全部设置。
- **范围外的子系统（可注入接口，默认关闭）**：
  - `user_memory`：`workflow.ts` 的 `user_memory_hooks.UserPreferenceMemorySystem`。没有注入时，`enable_user_memory=True` 走 Python 的 `ImportError` 分支：打 warning，并把 `enable_user_memory` 置为 False。`main.learn_from_user_edit` 抛出 `ImportError`。
  - `design_memory`：`design_memory_hooks.load_shared_retriever / reset_shared_retriever_cache`。没有注入时，`_load_design_memory_retriever` 返回 `(None, "design memory dependencies unavailable: …")`。`enable_design_memory=True` 时状态为 degraded 并记录错误，与 Python 缺少依赖时相同。
  - `knowledge_evolution`：编排代码不调用它，不需要接口。
  - 录制样例都使用 `--no-design-memory`、关闭用户记忆，所以默认路径与录制完全一致。

## 已知风险

- **WP23-2**：指纹字段，见上文。只要渲染引擎不记录浮点，任何会写出 manifest 的 Python float 文本，以及对其做哈希的地方，都会有同类问题。目前只发现这一处。
- 修复失败时写出的 `failure.json` 中，`traceback` 无法与 Python 逐字相同（真正抛出的异常才会有调用栈）。录制样例里只有未抛出的 `VerificationQualityError`。
- argparse 的帮助文本和少见的前缀冲突情形没有逐字复刻。
- `_optional_int_dict`：JS 无法区分 `1` 和 `1.0`，两条分支的结果相同（都是 `int(item)`），所以没有影响。

## 给下游的提示（WP24）

- 唯一剩下的端到端分歧是 `analysis_manifest_fingerprint`（9 个修复样例，见 ISSUES.md WP23-2）。复现：`npm run parity:runs -- --case refine`。要确认"除此之外全部一致"，可以复制 `tools/parity-runs.ts`，在快照比较处加上 `result.diffs = result.diffs.filter((d) => !d.includes('analysis_manifest_fingerprint'))`，以 `.mts` 运行。WP23 这样跑的结果是 9/9。
- 要让这个字段真正一致，需要第一期渲染引擎记录 Python 的 int/float（例如在 `json.dumps` 边界给每个数值打标记），或者由 WP12/WP24 在对照工具中把它列为归一化字段。WP23 没有改 harness 和 tools。
- `runRecordedPipeline` 会在每个样例前重置配置单例和环境变量。如果新增读取环境变量的模块级缓存，也需要在这里重置。
