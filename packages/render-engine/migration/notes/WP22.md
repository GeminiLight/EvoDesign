## 翻译要点与偏差

- **state**
  - 各模型基于 `py/pydantic.ts` 的 `BaseModel`，字段顺序、默认值与 Python 相同。
  - `EditOp` 实现了 `extra="forbid"`：每个多余键算 1 个错误，并与字段错误合并成一个 `ValidationError`。这样第一行的错误数（`N validation error(s) for EditOp`）与 pydantic 相同，这行文本会通过 `_coerce_to_edits` 进入迭代日志和报告。
  - 嵌套模型校验失败时，错误归到外层模型，与 pydantic 相同。
  - `int` 字段按 lax 模式校验：接受 bool、整数值浮点和整数字符串，拒绝 `1.5`。`max_iterations` 带 `ge=1, le=20`；`Dict[str, int]`、`Optional[float]`、`List[str]` 都有显式校验函数。
  - `canvas_library` 的 before 校验器与 Python 相同：先 normalize，再检查是否受支持；默认值不经过校验。
  - `EditOp.to_dict()`（`model_dump(mode="json")`）重建容器时保留 `PY_FLOAT_MARKS`。
  - 为对照框架导出了 `EditOp_to_dict`、`VerifierRefinerState_add_log/add_error` 包装函数。`EditOpName` 同时是类型和取值数组（`typing.get_args`）。
- **prompts**
  - `REFINER_LLM_SYSTEM_PROMPT` 由脚本从 Python 字面值生成成 JSON 字符串；Python 文本改动后需要重新生成。
  - Python 的 float 会打印成 `7.0`、`190.0`。TS 只在值所在容器带有 `PY_FLOAT_MARKS` 标记时才这样打印：`score=` 用 `_is_py_float(d, "score")`，location 和 context 的 JSON 先经过 `_with_py_floats`（复用 WP17 `sequence_layout.ts` 的工具）。
  - 字符串格式化（`:24s`、`:>5.0f`、`!r`、`[:n]`）都按码点和 Python 规则实现，非字符串、非数字会抛出与 Python 相同类型的异常。
- **llm_agent**
  - `RefinerLLMAgent(model=None)` 与 WP20 的做法相同：`model is None` 的路径放在 `static async create(model, max_retries, retry_delay_seconds)`，先检查 `require_model_capabilities("refiner", {"vision"})`，再创建模型。`new RefinerLLMAgent(null)` 会抛 TypeError 提示改用 `create`。
  - `propose_edits`、`refine_with_llm` 是 async。重试循环与 Python 相同：预算用尽时 break；永久性 HTTP 错误时 break；只有没拿到回答时才退避（`_sleep`，测试中可用 `_set_clock` 替换）。
  - `type(exc).__name__` 中的 `PyTypeError` 显示为 `TypeError`。
  - `build_manifest_summary` 的 `semantic_ids`、`bound_texts` 用 `Map`（id 可能形如整数）；`cap` 按 Python 切片语义处理（包括负数）；bbox 的 4 个值标记为 float。
- **refiner_report**
  - `_utc_timestamp` 用 `toISOString()` 截到秒再加 `Z`。
  - `write_refiner_report` 用 `pyJsonDumps(indent=2, ensure_ascii=False)`。路径拼接按 pathlib 规则实现（`_path_join`），文件头标注 server-only。
  - `build_markdown_report` 用 `IterationLog.model_validate` 重建迭代日志。
- **__main__**
  - argparse 换成只支持本 CLI 选项的小解析器（与 WP20 相同；`type=int` 的错误信息与 argparse 相同；帮助文本是简化版）。
  - `IterativeRefinerWorkflow` 在 `main` 中动态 import（Python 也是在函数内导入）。WP23 的文件出现之前，`main()` 走到这一步会失败。
  - 调用 `workflow.run(...)` 时把 keyword-only 参数按声明顺序变成位置参数：`(manifest_path, image_path, verifier_report_path, design_constraints, structure_path, layout_path, output_dir, canvas_library, max_iterations, skip_rerender_between_iterations, skip_checks, emit_markdown)`，没有传的参数用 `undefined`，以便使用默认值。
  - `main(argv)` 是 async，返回退出码。

## 已知风险

- `_coerce_to_edits` 对非 dict 条目输出 `type(item).__name__`。如果模型返回 `2.0`，TS 解析后的值是整数，会显示 `int`，而 Python 显示 `float`。录制中没有出现这种情况。
- 提示词能否打印成 `7.0`/`190.0` 取决于 `PY_FLOAT_MARKS`。WP23 读取 `verifier_report.json`（`initial_report`）时**必须**用 `pyJsonLoadsExact`，并且不能对 `subjective` 做 `structuredClone`，否则 `score=7.0` 会变成 `score=7`，`big_en_aes`、`ne_saas`、`iot_aes`、`t_class`、`t_er` 等样例的修复请求会出现分歧。Finding 的 bbox 已按 ISSUES.md WP22-1 处理。
- pydantic 校验错误只保证第一行一致。嵌套模型的错误数按每个嵌套字段 1 个计（pydantic 会展开计数）；这种情况只在 `EditApplyOutcome` 收到非法 edit dict 时出现，管线里不会发生。
- argparse 的帮助文本没有逐字复刻。
