## Coverage beyond the recorded vectors

Only 4 of the 30 recorded `apply_architecture_design_system` vectors actually rewrite the scene. All 4 use a layout-agent tier plan and style-agent colours. The other 26 return the manifest unchanged: the chart is not an architecture chart, the manifest has arrow labels, or the joined junctions would imply relations the graph does not have.

That leaves several paths with no real check from the parity suite:

- the role-based tier fallback and the barycentre pass
- `_split_tall_columns`
- `_orient_columns` mirroring
- fallback colours, plus muted/primary emphasis and the main path
- bidirectional and dashed connectors
- the diagram title

To cover them I generated variants from the 30 recorded inputs and ran each through Python (`.venv`, `PYTHONPATH=.`) and the TS port, comparing with `test/harness/compare.ts`. Scripts are in the session scratchpad, not the repo.

1. **240 variants (240/240 identical, 28 applied).** Each input was run with groups removed, edge labels removed, `layout_instantiation` on and off, `layout_specification` on and off, and emphasis plus a title added.
2. **393 variants (393/393 identical, 348 applied).** These used random subsets of architecture edges, with some reversed duplicates (bidirectional), `style: dashed`, and roles removed. Of the 348 applied:
   - 206 use the role-based fallback plan and 142 the layout-agent plan.
   - Python logged 147 moves of end-of-flow nodes, 84 column splits, 75 mirrorings and 79 rejected tier plans.

Not exercised by any vector or variant:

- `_spill_bottom_chains` actually moving nodes. It needs more than 5 bottom-row nodes and never triggered. The code is a line-by-line translation.
- The `EVODESIGN_AES_*` / `EVODESIGN_ARCH_DESIGN_SYSTEM` switches turned off. They go through `getEnv` with the same default `"1"` and the same off-set.

## Deviations and decisions

1. **Ties in `max(set(xs), key=xs.count)` (`_zones.name`).** Python iterates a `set` of strings in hash order, which depends on `PYTHONHASHSEED`. So when two zone names or roles tie, Python's own output is not deterministic. The TS helper `_mostCommon` breaks ties by first occurrence. No recorded or generated case diverged.
2. **Dict and tuple keys.** Lookup-only dicts are `Map`s: `by_id`, `neighbours`, `hosts`, `card_by_id`, `canon`, `pair_heads`, `arrow_by_edge` and the junction candidates. Tuple keys `(source, target)` are encoded as `JSON.stringify([s, t])`.
   - Junction candidates keep Python dict semantics: the first `(round(x, 1), round(y, 1))` key wins and the last colour wins. `-0.0` and `0.0` count as the same key.
3. **`int(s, 16)`.** This is used for the text and arrow `seed` and inside `_hex`. It goes through the local `_int16`, which applies CPython's literal grammar: whitespace, a sign, an optional `0x`, and underscores only between digits. It then calls `pyInt`. The reason: `pyInt` on its own strips every `_`. A non-hex text id raises `ValueError`, as in Python. That can happen when an existing bound text keeps its id and the id does not start with 8 hex characters.
4. **`f"{v:02X}"` in `_mix`.** Ported as `_format02X`, which also handles negative values the way Python does (`-F`).
5. **`"strokeWidth" in styling`.** `styling` is `(layout_instantiation or {}).get(id) or {}`. `_contains` handles dict, str and list the way Python's `in` does. A str `styling` then raises `TypeError` on indexing, as in Python.
6. **`host.update({...})`.** Ported as `Object.assign` after evaluating the whole literal first, so `customData` and `version` are read before the update, as in Python.
7. **`_Card.display_title` / `display_sublabel`.** Python creates these attributes inside `_layout`. In TS they are declared fields initialised to `''`.
8. **Methods that return `None`.** These are `_assign_service_hues`, `_layout`, `_orient_columns`, `_move_backward_sinks`, `_split_tall_columns` and `_spill_bottom_chains`. They return `null` and mutate in place, like Python. Slice assignment `xs[:] = ...` is done with `splice`, so it acts on the same array.
9. **`architecture_style_normalizer`.** The role dicts are `Map`s. `str(element.get("containerId", ""))` keeps Python's `"None"` text for a null `containerId`. That text is truthy, so the `min(16, int(fontSize))` branch runs, exactly as in Python.

## Known risks

- Hash-order ties, as in decision 1.
- `pyLower` / `pyIsupper` use JS case mapping. This only matters for exotic characters in labels; it is shared WP01 behaviour.
- `deepcopy` is `structuredClone`. Inputs are JSON values; a `Map` or `Set` in a manifest would be cloned but would not round-trip as Python dict semantics.

## Hints for downstream (WP09/WP10)

- Entry points:
  - `apply_architecture_design_system(manifest, structure_instantiation, layout_instantiation = null, layout_specification = null, design_constraints = '')`
  - `normalize_architecture_style(manifest, structure_instantiation, layout_instantiation = null)`
- Both deep-copy and return a new manifest. `apply_*` returns the **same object** it was given whenever it bails out.
- `apply_*` throws a Python-style error (`ValueError`, `TypeError` or `KeyError`) in the same situations Python raises.
- WP09 can import `title_element`, `has_cjk`, `aesthetic_enabled`, `emphasis_of`, `is_enabled`, `_text_width` and `_stable_id` directly from `architecture_design_system.ts`.
