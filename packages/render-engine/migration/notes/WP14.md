## 关键实现说明

### canvas_render：出图走进程内 Node playwright
- Python 调 `npx tsx tool_services/scripts/render-excalidraw.ts --scene - --output … [--width/--height/--timeout/--margin/--scale]`，stdin 是 `json.dumps(data, ensure_ascii=False)`。TS 保留完全相同的命令行构造（`_append_cli_args`、`_resolve_script_path`、`workdir`）和 `subprocess.run` 的契约（`CompletedProcess{returncode, stdout, stderr}`、`TimeoutExpired`），只是 `subprocess.run` 遇到“默认 runner + 默认 Excalidraw 脚本”时，不起子进程，而是在进程内执行 `_run_excalidraw_cli(argv, stdin)`——它是 render-excalidraw.ts（含 `src/lib/renderDefaults.ts`、`renderContract.ts`）的逐行移植：同样的参数解析与校验、`chromium.launch(headless, 同样的 args)`、`deviceScaleFactor: 2`、`setViewportSize`（原脚本没有 await，这里也不 await）、`waitForFunction` 竞态、错误文本、写文件。stdin 仍然先 `pyJsonDumps` 再 `JSON.parse`，与原来的 JSON 往返一致。
- 渲染 URL 与原脚本一样在调用时读 `EXCALIDRAW_RENDER_URL`（经 `py/env.ts getEnv`），`EXCALIDRAW_EXPORT_SCALE` 同理。
- 其他命令（TLDraw 脚本、自定义 `runner`/`script_path`）用 `child_process.spawn` 真正起子进程，行为与 Python 相同。
- `subprocess` 是可替换的模块对象（对应 Python 测试里 monkeypatch `canvas_render.subprocess.run`）；`_set_smart_crop` 对应 monkeypatch `smart_crop`。
- `render`、`render_canvas` 及其上层（service、rendering、environment 的出图方法、adapter 的 render_*）都是 `async`，调用顺序不变。`smart_crop` 保持同步。
- `render_canvas(data, output_path, canvas_library, kwargs)`：Python 的 `**kwargs` 是末尾对象参数（snake_case 键），未知键抛 `TypeError`，与 Python 一致。
- 异常类：`FileNotFoundError`、`PyTimeoutError`（`name='TimeoutError'`）、`TimeoutExpired` 在本模块定义；`render_png_result` 的错误串 `f"{type(exc).__name__}: {exc}"` 用 `error.name`。

### service：RenderWorkflow 走 LangGraph.js
- Python 的 `RenderWorkflow.run` 调用编译后的 LangGraph `StateGraph(WorkflowState)`；端到端录制里每个渲染节点之后都有快照。第一期的 TS `RenderWorkflow`（WP10 的文件）是同步的顺序执行器，第一期工具（parity-stages 等）依赖它同步，所以没有改它。`service.ts` 的 `_run_render_workflow` 用 WP13 的 `PydanticStateGraph` 把 `render_wf._excalidraw_nodes()` 里**同一批节点函数**按同样的节点名、线性边编成 LangGraph.js 图运行（`ensure_no_integer_like_semantic_ids` → `graph.invoke` → `WorkflowState(**result_dict)`，与 Python `run` 相同）。
- 状态类 `_RenderGraphState`（继承第一期的 `WorkflowState`，`pythonName = 'evodesign.agentic_system.render_engine.state.WorkflowState'`）在构造时模拟 pydantic 的重新校验：`Dict` 字段浅拷贝、`List[Dict]` 字段逐项浅拷贝。这影响结果：Python 在 convert 节点之后 `manifest_without_arrows` 与 `diagram_manifest` 指向同一个 dict，下一个节点拿到的是两个不同的浅拷贝；不模拟的话后续阶段替换顶层键时 `manifest_without_arrows` 会跟着变，节点快照就会不同。上面的 279 个节点快照全部一致。
- `json.dump(manifest, indent=2, ensure_ascii=False)` → `pyJsonDumps(..., {indent: 2, ensureAscii: false})`。TS 无法区分 `1` 和 `1.0`，所以写出的 JSON 文本里整数值浮点会少 `.0`；端到端对照按解析后的值比较 JSON 产物，不受影响。
- `output_dir=None` 时用 `mkdtemp(<tmpdir>/evodesign-render-XXXXXX)`，与归一化规则里的前缀一致。

### image_cropper：纯 TS 复现 OpenCV
- `cv2.imread`（IMREAD_COLOR）：pngjs 解码后取 RGB，透明通道直接丢弃（不合成），灰度复制成三通道，调色板展开，16 位取高字节（`skipRescale`）。只支持 PNG（渲染器只产 PNG）；其他文件按 cv2 读不出处理，返回 `Error: Could not read image at …`。
- Excalidraw 分支：与左上角像素逐通道最大差 `> 2` 作为内容掩码。
- TLDraw/其他分支：`BGR2GRAY` 定点公式 `(B*1868 + G*9617 + R*4899 + 8192) >> 14`；Otsu 阈值按 OpenCV `getThreshVal_Otsu_8u`（double 累加、`FLT_EPSILON` 判定、严格大于才更新）；`morphologyEx` 用矩形最小/最大滤波，图外像素不参与（等价于 OpenCV 默认边界值），`iterations=n` 的 5×5 全 1 核等价于一次 `(4n+1)²` 核。
- `cv2.imwrite`：写 8 位 RGB PNG（颜色类型 2，与 cv2 写三通道图相同），字节与 libpng 不同，像素相同。
- 空图时的异常与 Python 一致：Excalidraw 分支 `IndexError`（numpy 索引 `[0, 0]`），其他分支 `cv2_error`（`name='error'`，对应 `cv2.error`）。
- Python 里是 LangChain `@tool`，只以 `smart_crop.invoke({...})` 调用；TS 导出同名对象，`invoke(input)` 签名相同，另导出 `_smart_crop` 普通函数。
- **差分核对**（临时脚本，未入库）：Python 与 TS 对同一批输入分别 `smart_crop.invoke`，比较返回文本和 `cv2.imread(IMREAD_UNCHANGED)` 读回的输出像素与 PIL 模式：
  - 253 例：示意图（白/浅色/深色背景、1 像素虚线、浅色边框）、随机色块、随机噪声、RGBA（含 alpha=0 与半透明）、L、LA、调色板、16 位灰度、16 位 RGB、带底部水印的大图、空白图、3×2 小图、非图片文件；每张图 × 3 种引擎（excalidraw/tldraw/其他）× padding {0, 8, 60}，以及显式 `bottom_offset/top_left_margin` 的组合。253/253 一致。
  - 150 例 Otsu/形态学压力测试（均匀噪声、近似纯色、稀疏小块、渐变、三值图）：150/150 一致。
  - 录制样例：上表 41 + 10 + 31 条裁剪后的产品图，与 Python 产物像素相同。

### png_validation：复现 Pillow 的 open + verify
- 逐条对应 `PngImagePlugin._open` 与 `ChunkStream.verify` 的检查（见文件头注释）：签名、IDAT 之前的块（类型 `\w{4}`、数据完整、CRC），IHDR 的模式/尺寸/滤波方式，`verify` 从第一个 IDAT 读到 IEND 并校验 CRC。分类到 Python 的四种结果：不存在 / 空文件 / unreadable（`UnidentifiedImageError`）/ corrupt（`OSError`、`SyntaxError`），非 PNG 图片按文件头识别 Pillow 会报的 `format`（JPEG/GIF/BMP/WEBP/TIFF/ICO/PSD）。Pillow 不捕获的异常（截断 IHDR 的 `ValueError`、IEND 在 IDAT 之前时 `verify` 里的 `IndexError`）也照样抛出。
- **差分核对**：200 个文件（正常 PNG、带 tEXt、27 种截断位置、136 处单字节翻转、缺 IHDR、IEND 提前、非法模式/滤波方式/零尺寸/IHDR 过短、尾部垃圾、缺 IEND、6 种其他图片格式、文本、空文件、不存在），Python 与 TS 的结果（成功或 `异常类: 消息`）200/200 相同。

### editing：差分核对
`apply_operations` / `assert_preserves_locks` 没有向量。用 Python 生成随机场景（数字形式的 id、卡片 `evoDesignCard` 及图标/副标题、锁定元素、已删除元素、带绑定和标签的箭头、`files`）和随机操作批次（6 种操作，合法与非法参数混合，scope/locked），两边分别执行，比较 `(result, changed)` 或 `EditError(code, message)`，以及 `assert_preserves_locks` 的结果，同时检查键顺序：两轮共 9000 例全部一致（成功 1278 例，其余覆盖全部 11 种错误码）。`by_id`/`old`/`new` 用 `Map`（id 可能是数字字符串，普通对象会重排键，而 `changed` 的顺序跟随 `by_id`）。

## 偏差与已知风险

1. **整数与浮点**：`_validate_positive_int` 无法区分 Python 的 `4000` 和 `4000.0`（后者 Python 会拒绝）；`str(float(render_scale))` 用 `floatRepr`，渲染器收到的 `--scale` 文本相同。
2. **进程内渲染**：原脚本作为独立进程运行，`console.warn` 写 stderr；TS 把同样的文本收集到 `CompletedProcess.stderr`。`npx` 自身打印的警告不会出现（见上文失败路径对比）。超时：Python 的 `subprocess.run(timeout=…)` 会杀掉子进程；进程内时用 `Promise.race` 抛同样的 `TimeoutError` 文本，后台的 playwright 调用会在它自己的超时后结束并关闭浏览器。
3. **`Path.resolve()`**：Python 会解析符号链接，TS 的 `path.resolve` 不会；只影响 `cwd`/脚本路径的字符串，不影响出图。`Path(output_path)` 的规范化（`a//b`、`./x`）未模拟，调用方给的都是规范路径。
4. **TLDraw**：`TldrawRender` 已移植（起真实子进程），但第一期的 TS `RenderWorkflow` 不支持 tldraw，所以 `render_manifest(canvas_library='tldraw')` 会在构造工作流时报错；`validate_manifest(..., 'tldraw')` 抛 `NotImplementedError`。均不在本期范围。
5. **png_validation**：只复现 PNG 插件的检查；非 PNG 文件按文件头猜格式，Pillow 对这些格式自身的解析错误（如头部截断的 JPEG 会变成 unidentified）未模拟。
6. **image_cropper**：只读 PNG；gAMA/iCCP 等色彩信息两边都不应用（cv2 不应用，pngjs 也不应用）。

## 给下游的提示

- 出图入口都是 async：`await render_manifest(...)`、`await render_png_result(...)`、`await new CanvasEnvironment(cfg).render_png(...)`。参数按 Python 声明顺序全部是位置参数（keyword-only 也一样），例如 `render_png_result(manifest, output_path, 'excalidraw', 4000, 4000, ANALYSIS_RENDER_SCALE, false)`。
- `from evodesign.canvas_environment import X` → `import { X } from '../canvas_environment/index.ts'`（或直接从子模块导入）。
- `require_generation_capability(canvas_library, mode)` / `require_refiner_capability(canvas_library, mode)` 已存在，WP13 `agentic_system/config.ts` 的懒加载现在能找到它们（可以改成静态导入，那是 WP13 的文件，本 WP 没有改）。
- 渲染需要 `EXCALIDRAW_RENDER_URL`（回放时为 `http://127.0.0.1:3001/renderers/excalidraw`），每次出图启动一个新的 headless Chromium（约 1.5–5 秒）。
- `service.render_manifest` 的渲染图节点由 `PydanticStateGraph` 构建，`test/harness/runs.ts instrumentSnapshots()` 会自动采集这 9 个节点的快照；必须在 `instrumentSnapshots()` 之后调用（它修补的是 `StateGraph.prototype.addNode`，图在每次调用时新建，所以不需要提前构建）。
- `EditError` 继承 `ValueError`，有 `code` 属性；`apply_operations` 返回 `[result, changed]`。
