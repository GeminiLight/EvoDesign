  - 验证：Python 生成 2737 个变异 JSON 串（截断、插入、删除、BOM、代理对、控制字符等），strict / strict=False / raw_decode 三种调用，TS 与 Python 结果（值或 `msg,pos,lineno,colno,str`）7630/7630 相同。
- `src/py/yaml.ts`：`yaml.safe_load` 的子集（块映射/序列、注释、流式序列、引号字符串、YAML 1.1 的 null/bool/int/float）。不支持的语法直接抛 `YAMLError`，不猜。`configs/*.yaml` 与 `evodesign/config/defaults/*.yaml` 共 5 个文件与 PyYAML 结果完全相同。第二期不允许加依赖，所以没有用 yaml 包。

## 关键实现说明

### utils/llm_output
- 所有 JSON 解析走 `json_decoder.ts`；`_extract_balanced_json_substring`、`_loads_json_span`、`_loads_embedded_json` 的下标按码点（与 Python 一致）。`_split_json_strings`/`fix_json_string` 用 UTF-16 下标也能得到相同的切分（代码里注明了原因）。
- 正则里的 `\s` 用 Python 的空白字符集（`str.isspace()`），`\w` 用 `[\p{L}\p{N}_]`。
- `get_text_from_response`：Python 用 `hasattr(response, 'content')` 区分消息对象和 dict。TS 规则：普通对象（原型为 `Object.prototype`）= dict，没有属性；类实例（LangChain 消息等）= 有属性的对象。adapter 用同样的规则把向量里的 `__message__` 还原成真正的 `AIMessage`/`HumanMessage`。
- 额外做了差分测试：3125 个类 LLM 输出（围栏、前后缀、`<think>`、XML 包裹、截断、尾逗号等及其随机变异），`convert_json_output` 宽松/严格两种模式下 TS 与 Python 的返回值或异常（`str`、`msg`、`pos`）6250/6250 相同。

- `create_agent(..., system_prompt=str)` → `createAgent({ systemPrompt: new SystemMessage(str) })`（WP12 提示：传字符串会变成 content parts）。`valid_agent_arg_list` 的 snake_case 键映射到 createAgent 的 camelCase 选项。
- `_invalid_output_echo` / `_preview_response` 的截断按码点。
- 异常分类：Python 对 builtin / httpx / openai / anthropic 异常类的 `isinstance` 判断改为按原型链上的类名、`status`/`status_code`、Node socket 错误码（ECONNRESET 等视为 OSError）判断。`_HTTP_STATUS_ERROR_TYPES`（httpx.HTTPStatusError）与 `_PROVIDER_STATUS_ERROR_TYPES`（openai/anthropic APIStatusError 及其子类，名单取自 openai-python）分开定义，与 Python 相同；`_is_retryable_exception` 的状态码分支对应 `isinstance(exc, _HTTP_STATUS_ERROR_TYPES + _PROVIDER_STATUS_ERROR_TYPES)`，另加一条：openai-node 没有 APIStatusError 类，未映射的状态码抛的是带 `status` 的普通 `APIError`，因此 `_PROVIDER_API_ERROR_TYPES` 且有状态码时也走这一分支（openai-python 在这种情况下抛 APIStatusError）。保留了 Python 的一个特性：openai 的 `APIConnectionError` 是 `APIError` 子类，没有状态码时走"按消息关键词"分支，因此默认不重试。

## 偏差与已知风险

1. **异常分类**：Python 按异常类判断，TS 按类名/状态码/错误码判断。LangChain.js 会把 openai 的连接超时包装成 `name='TimeoutError'` 的普通 Error，因此 TS 会重试这种超时；Python 中 `openai.APITimeoutError` 属于 `APIError` 分支，消息里没有关键词时不重试。`_is_stream_transport_error` 中"openai._streaming 里抛出的 JSONDecodeError"改为看调用栈中的 openai/anthropic 流式代码，属于近似。
2. `_call_model_once` 中 "NoneType ... not iterable" 的判断额外接受 JS 的 "null/undefined ... not iterable"。
3. JSON 中键形如整数的对象（`{"2":…,"1":…}`）解析为 JS 对象后键顺序会变（Python 保持插入顺序）。大模型输出里的键一般是 id/字段名，影响不大；如有下游需要，应改用 Map。超过 2^53 的整数会丢精度。
4. `_render_template` 用 `pyStr` 转换变量值：JS 数字无法区分 `1` 和 `1.0`，变量是浮点数时与 Python 的 `str()` 可能不同（目前模板变量都是字符串）。
5. `pydantic.ts` 只实现了状态模型需要的部分；字段类型校验是宽松的近似，错误消息逐条措辞与 pydantic 不同。
6. `image_to_data_url` 缩放比 Python 慢（纯 JS），每张 1–3 秒。

## 给下游的提示

- **状态类**：继承 `WorkflowStateBase`，`static override model_fields = { ...WorkflowStateBase.model_fields, 新字段: field({...}) }`，字段用 `declare` 声明（不要写类字段初始化，否则会覆盖基类构造函数写入的值）。设置 `static override pythonName = 'evodesign....state.WorkflowState'`，快照的图名才会被比较。
- **工作流**：`class X extends BaseWorkflow<S>`，在 `_build_workflow()` 里用 `this.workflow.addNode/addEdge/addConditionalEdges`（`START`/`END` 从 `@langchain/langgraph` 导入），最后 `return this.workflow.compile()`。`_build_workflow()` 在 `super()` 里执行，此时子类构造函数体还没运行；节点函数里再访问子类属性。节点名不能与状态字段同名（LangGraph.js 与 Python 规则相同）。
- **Agent**：`super(model, system_prompt, task_prompt, tools, { strict_json_output: true, ... })`；`await this.invoke({...})` / `await this.invoke_with_history(messages)`。JSON 解析错误一律是 `PyJSONDecodeError`（`src/py/json_decoder.ts`），`instanceof` 判断即可。
- **模型创建**：`await LLMFactory.create_for_role('router')`。`runRecordedPipeline`（WP23）在创建任何模型前调用 `set_chat_model_factory(options.chatModelFactory)`，结束后传 `null` 恢复。
- **运行预算**：`await llm_run_budget_from_env(async () => {...})` 包住一次工作流运行（对应 `workflow.py` 的 `with llm_run_budget_from_env():`）。
- **环境变量**：`env_loader` 在导入时把仓库根目录 `.env` 读进 `process.env`（不覆盖已有值）。WP23 应在导入流水线模块之前把 `input.env` 写入 `process.env`，或者写入时覆盖所有 `input.env` 的键（录制时 `.env` 中的键在 `input.env` 里都显式置空了）。
- **严格 JSON 解析**：其他模块需要 Python `json.loads` 的报错文本或位置时，使用 `pyJsonLoadsExact` / `pyJsonRawDecode`，不要用 `pyJsonLoads`。
- 依赖 WP14 的 `canvas_environment/capabilities.ts` 和 WP16 的 `generation_stage/styling/colorful.ts` 时是懒加载的；这两个文件的导出名必须与 Python 相同（`require_generation_capability(canvas_library, mode)`、`require_refiner_capability(canvas_library, mode)`、`PALETTES`、`render_palette_card`）。

## 修复轮 2：image_to_data_url 阻塞 vitest worker，及高图的像素差异

**问题 1（复核发现）**：第一期命令 717/717 通过，但 vitest 报 1 个未处理错误 `[vitest-worker]: Timeout calling "onTaskUpdate"`，退出码 1。原因：`functions.test.ts` 在一个同步的 `it` 里跑完 `image_to_data_url` 的 48 条向量，旧实现合计约 55 秒同步计算（pngjs 解码/编码 + 逐通道逐像素的重采样），阻塞 worker 事件循环，vitest 的 RPC 超时（60 秒）。这一轮之前的笔记没有提到这个错误。

根本修复是让函数本身变快（Python 是同步函数，测试框架也是同步调用，所以保持同步签名；运算结果逐位不变）：
- 重采样：按通道数展开内层循环；竖向一遍改为按行累加（行优先，一次扫 4 行），不再按列跨行读取。累加器用 INT32（`Math.imul` + `|0`），与 Resample.c 的 INT32 相同；整数加法在模 2^32 下满足结合律，求和顺序不影响结果。
- PNG 解码：非隔行 8 位 PNG 直接 inflate + 反滤波到原通道数（pngjs 会先展开成 RGBA，再由我们挑回通道）；隔行 PNG 仍走 pngjs。
- PNG 编码：自写（IHDR/IDAT/IEND，CRC32），zlib 级别 6（Pillow 默认的 `compress_level`），每行自适应滤波（绝对差之和最小）；pngjs 默认级别 9，很慢。
- adapter 的像素比较同样改为直接反滤波后取哈希（同颜色类型 + 同像素字节 ⇔ 同像素），不再用 pngjs 展开两张约 3000 像素宽的图。
- 结果：48 条向量的纯计算从约 46 秒降到约 19 秒；vitest 里该测试约 23–27 秒（含 adapter），第一期命令 717/717、退出码 0、无未处理错误；`PARITY_WP=WP13` 78/78 测试，同样无未处理错误。生产中每张 4 倍导出图约 0.2–0.6 秒（原 1–3 秒）。

**问题 2（复查时发现，旧实现就有）**：用合成图复查时发现高图（缩小的行数远多于列数）与 PIL 差 1（RGB）到 16（LA）。用旧重采样代码复算结果相同，说明不是这一轮引入的。原因：Pillow 13 的 `ImagingResample` 会在 `(输入高 - ysize) >= 1 且 (输入高 - ysize) > 2 × (输入宽 - xsize)` 时**先做竖向一遍**（整幅宽度，之后横向一遍不裁行），否则先横向（原实现只有这一种）。两种顺序的中间图取整不同。规则读自已安装 `_imaging` 模块中 `_ImagingResample` 的反汇编（`cmp w10,#1; lsl w9,w9,#1; ccmp w10,w9,#4,ge; cset w23,le`，w10 = 输入高 − ysize，w9 = 输入宽 − xsize），并用 300 组随机尺寸（RGB 噪声图，`reducing_gap=None`）核对：两种顺序结果不同的 298 组 + 1 组大图，规则 0 个误判。现有 48 条向量都是宽图，不受影响，所以之前没有发现。
- 复查用的合成图（临时脚本，未入库）：RGB 5071×2750、RGBA 4000×2600、L 3500×900、LA 1200×3300、RGBA 13000×700（2×2 reduce）、RGB 600×13001（2×2 reduce，高图）、RGB 301×77、LA 90×9000（高图 + reduce）、RGBA 2×9→1×1、L 3073×3073；与 PIL `image_to_data_url(max_edge=...)` 的解码像素 10/10 相同（修复前 7/10）。
- 另核对了 La/RGBa 与 LA/RGBA 互转在 alpha=0、128、溢出时与 Pillow 相同（La→LA 在 alpha=0 时保留灰度值，与 TS 一致）。
