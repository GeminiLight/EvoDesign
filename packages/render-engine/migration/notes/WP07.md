## Adapters (nothing is skipped)

- **`test/adapters/…arrow_routing.ports.ts` → `_plan_edges`.** Fixtures decode the `DiagramContext` dataclass as a plain object of its fields. The port reads the `is_architecture` property, so the adapter rebuilds the instance with `DiagramContext.from_fields`.
- **`test/adapters/…arrow_adder.ts` → `_route_edge`, `_route_context`, `_keeps_edge_label`.** These do the same rebuild for `DiagramContext`, and for `PortTotals` via `PortTotals.from_fields`. The tuple-keyed counters arrive as `Map`s with array keys, and the adapter turns them into `TupleDefaultDict`s.
- **`test/adapters/…arrow_routing.passes.ts` → `_reduce_crossings`, `_route_concept_corridors`.**
  - In Python, `elements_by_id[id]` is the same dict object as the arrow in `arrow_elems`, because `arrow_adder` builds both from `new_arrows`. A committed reroute therefore also changes the `elements_by_id` entry.
  - JSON fixtures lose this aliasing. The adapter restores it for entries that are structurally equal (`pyEq`) to the arrow with the same id. This is the same technique as WP04's `shape_size_fitter` adapter.

## Deviations and decisions

1. **`_ROUTE_MEMO` (ContextVar).**
   - It is ported as a minimal `ContextVar` class in `grid_router.ts` with `get`/`set`/`reset(token)`, holding `Map<string, Point[] | null> | null`.
   - `add_excalidraw_arrows_to_manifest` owns it exactly like Python: set to a fresh `Map` only when unset, and reset in `finally`.
   - Memo hits and the first store both return copies (`route.map(p => [p[0], p[1]])`), because TS tuples are mutable arrays.
2. **`_route_memo_key`.** TS has no int/float distinction, so the key prints the geometric values with float repr (`floatRepr`):
   - start, end, obstacles, clearance and port normals;
   - each arrow's `x`, `y` and `points` numbers.

   `type`, `isDeleted` and `opacity` use `pyRepr`. Arrow `points` print as lists of lists. This reproduces Python's `repr` for all 120 vectors. The key only has to be injective for the cache, so a hand-built arrow with integer coordinates would produce a different (still unique) key string, with no effect on routes.
3. **Dijkstra in `_find_orthogonal_visibility_route`.**
   - A binary heap is ordered by `(cost, serial)`. Serials are unique, so its pop order is identical to `heapq`'s and ties are broken by the serial counter.
   - Grid points, states and edge-crossing caches are keyed by the string `"${x},${y}"`. `String(-0) === "0"` matches Python's equal hash/equality for `0.0` and `-0.0`.
   - Python builds `rows`/`columns` by iterating a `set` and then sorting each group by the other coordinate. The port walks the sorted `xs`×`ys` grid instead, which yields the same ordered lists and does not depend on set order.
   - `xs`/`ys` use a numeric sort. Python's `sorted` on non-NaN floats gives the same result.
4. **`defaultdict` fields.**
   - `PortTotals.corridor_counts`, `source_port_counts` and `target_port_counts` (tuple keys) are `TupleDefaultDict<number>`, a `Map` subclass matching keys by value. Iteration yields the first-inserted tuple, so it compares like the Python dict. `getItem(key)` is `d[key]` and inserts 0; `get` is `d.get`.
   - `source_degrees` and `target_degrees` (str keys) are plain objects read through `_defaultdict_int_getitem`, which inserts 0 on a missing read like `defaultdict`. This applies to `_route_context` and `_reroute_architecture_edges`.
5. **Set iteration in `_assign_port_ranks`.** Python iterates `source_groups.keys() & target_groups.keys()` in hash order. The port walks `source_groups` in insertion order. Each key writes only its own count entries and only `*_port_index` fields of its own endpoints, so the order cannot change the result.
6. **Dataclass properties.** `DiagramContext.is_architecture` and `is_concept_map` are getters on the prototype, so `compare` sees only the six dataclass fields. `from_fields` exists for adapters and any future caller holding decoded dataclass data.
7. **`_should_drop_edge_label`.** `ref is target_ref` is ported as "first loop iteration (or `===`)". The second iteration can only match when the source and target labels differ, so identity versus equality cannot differ there.
8. **Void functions return `null`.** Python returns `None`, and the vectors check the return value.
9. **Dict versus `Map`.**
   - Scene-local dicts keyed by element id use `Map`, so key order never depends on JS integer-like key ordering. This covers the `labels.py` arrows/labels/paths/faces maps, the `rebuild_excalidraw_arrows` `old_arrows` map and the `sequence_layout` lookup maps.
   - `route_contexts`, `elements_by_id`, `id_map` and `store` stay plain objects. Their keys are 20-hex element ids or semantic ids, which are never canonical array indices.
10. **`sequence_layout`.** It uses WP02's `generation_stage.layout.element_shape_estimator._estimate_text_dimensions`, as the Python import does, not the converter one. `arrow_adder` imports `sequence_layout` statically. Python imports it lazily, but there is no cycle in TS because `sequence_layout` does not import `arrow_adder`.

## Known risks

- **Int versus float.** Float-only formatting matters only in `_route_memo_key`, which is cache-internal. All emitted manifest numbers come from arithmetic and compare numerically.
- **Unhandled `TypeError` cases.** Python raises `TypeError` on some malformed inputs that never occur in practice, for example `opacity: None` compared with `> 0` in `_position_architecture_bound_labels`. The port follows JS semantics there (`null > 0` is `false`). No vector exercises these cases.
- **Performance.** The full WP07 parity run takes about 24 s. The 112-case arrow stage takes about 9 s in total, so the grid router is not a bottleneck in TS.

## Notes for downstream (WP10)

- **Stage entry point.** It is `add_excalidraw_arrows_to_manifest(manifest, structure_instantiation)`, and the remaining Python keyword-only parameters are positional: `(port_spacing = null, _adaptive_ports = true, _report_crossings = true)`. `RenderWorkflow._run_excalidraw_arrow_adder` then calls WP08's `normalize_architecture_style(manifest, structure, layout_instantiation)`.
- **Rebuild path.** `rebuild_excalidraw_arrows(manifest, structure)` is the unified-mode rebuild entry, with 14 vectors passing.
- **Pass outside an arrow pass.** Do not call `_orthogonal_visibility_route` outside an arrow pass expecting memoization. With `_ROUTE_MEMO` unset it just computes, which is the same as Python.
