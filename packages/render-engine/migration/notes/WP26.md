# WP26 对照数据：backend 网页出图流程的事件流

## 做了什么

- 新增 `tools/record_web_runs.py`（`npm run record:web`）：在进程内驱动 backend 完整模式出图入口，用第二期的 cassette 替身模型录制 28 个用例，每个录两次、归一化后比较；`--replay` 用录好的 cassette 回放并与 fixture 比较。
- 新增 `fixtures/web_runs/<case>/`（28 个用例，约 28 MB），索引 `_index.json`、回放结果 `_replay.json`、日志 `_logs/`。
- 新增 `test/harness/web_runs.ts`：加载用例、归一化（与录制端同规则）、事件 / 结果 / 模型请求的比较，给出第一处分歧的精确路径。
- 新增 `tools/parity-web.ts`（`npm run parity:web`）。`package.json` 只加了 `parity:web`、`record:web` 两个脚本。

## 录制入口与条件

真实调用链（前端 `apiDiagramService.generateDiagramStream` → `POST /api/v1/diagram/generate/stream`）：

```
app.api.v1.endpoints.diagram.generate_diagram_stream（用未装饰的 __wrapped__，访客）
  → WorkflowGenerateService.generate_without_render_streaming
  → WorkflowEngineAdapter.stream_without_render → workflow_runtime/*
  → Text2DiagramWorkflow.begin_generation_run / run_generation_stage、render_manifest、
    VerifierWorkflow、IterativeRefinerWorkflow.prepare / run_prepared
  → DiagramStreamService.rewrite_chunk（访客：原样透传，不持久化）
  → with_sse_keepalive（StreamingResponse 的 body_iterator）
```

- **持久化：选"直接调用 adapter 层"这一种**。具体做法是以访客身份调用 endpoint 函数本身（这样 endpoint 的错误映射 `stream_errors` 也在录制范围内）。访客请求不会持久化，也不读 DNA；endpoint 的 `db`、`guest_quota` 依赖用替身（只有 commit/rollback 空操作，额度不限），写法与 `tests/backend/test_diagram_endpoint.py` 相同。整个过程不打开任何数据库。
- **设计记忆关**：`design_memory_enabled=False`、`design_memory_learning=False`，memory 阶段报 `status=disabled`。
- **Settings**：用 `Settings(_env_file=None, …)` 构造，不读 `.env`。LLM 字段都是固定的非机密占位值（`cassette-model`、`http://127.0.0.1:9/v1`、temperature 0.0、max_tokens 16384）。`auto_refine_enabled`、`auto_refine_max_iterations` 取自用例（backend 默认为开、2）。`retain_generation_artifacts=False`，与生产默认一致：请求目录在结束时删除。
- **模型**：全部走 `tools/llm_cassette.py`，答复由 `tools/cassette_synth.py` 合成。共 121 次模型调用，其中合成 / 故障合成 / 故障错误分别为 25 / 3 / 2 个用例出现，**真实调用 0 次**。
- **渲染**：正常的渲染子进程，`EXCALIDRAW_RENDER_URL=http://127.0.0.1:3001/renderers/excalidraw`。
- **环境**：与第二期相同（`CASSETTE_ENV`，`PYTHONHASHSEED=0`），`PYTHONPATH=<repo>:<repo>/backend:tools`。
- **引擎参数**：backend 总是用默认参数构造 `Text2DiagramWorkflow`（multiagent、critic 开）。unified（oneshot）和 critic 关这两类用例，通过 adapter 自带的依赖注入点传入参数：`WorkflowEngineAdapter(streaming_dependency_loader=…)` 返回生产用的 `StreamingEngineDependencies`，只把 `workflow_cls` 换成 `functools.partial(Text2DiagramWorkflow, **engine)`。没有改动 backend 代码。参数记在 `input.json` 的 `engine` 字段。
- **补充的故障类型**：`llm_error`，模型调用直接抛 `ValueError`。实现方式是在 `record_web_runs.py` 里扩展 Synthesizer，没有改第二期的 `cassette_synth.py`。这种故障在 cassette 里记为 `{"error": {"type": "ValueError"}}`，Python 和 TS 两侧的 cassette 都能回放。

## 每个用例目录

| 文件 | 内容 |
|---|---|
| `input.json` | 用例 spec、HTTP 请求体（与 `buildGenerateDiagramPayload` 的形状一致）、settings、engine、环境变量 |
| `cassette.jsonl` + `images/` | 模型调用，格式与 `fixtures/runs` 相同 |
| `events.jsonl` | SSE 事件序列 `{index, event, llm_calls, data}`；`llm_calls` 表示该事件发出前已发生的模型调用次数（adapter 生成器在两个 chunk 之间处于挂起状态，所以计数是准确的），用来确定模型调用与事件的先后；keepalive 注释行已去掉 |
| `result.json` | `{result: result 事件 data, error: error 事件 data}` |
| `frontend.json` | 前端 `generateDiagramStream` 会触发的 callbacks 序列，以及它从 result 映射到 `DiagramResponse` 的字段（报错时为 ApiError） |
| `artifacts/` + `artifacts.json` | adapter 删除请求目录前一刻的完整拷贝（已归一化），包括前端最终看到的 PNG |
| `_meta.json` | keepalive 次数、请求目录是否已删除（不参与比较） |

## 归一化

沿用 `tools/run_normalize.py` 的全部规则，另加两条（Python 端在 `WebNormalizer`，TS 端在 `test/harness/web_runs.ts`）：
1. `req_<12 位 hex>` 替换为 `req_<ID>`：request_id 来自 uuid4，请求目录路径里也带它。
2. 键名以 `_ms` 结尾的数值、`timings_ms` 下的全部数值、`elapsed_seconds` 都替换为 0：包括 `duration_ms`、`total_duration_ms`、`optimizations.*_ms` 等墙钟时间。

## parity:web 的两种模式

- **在线模式**（默认）：加载 `src/web_runtime/index.ts` 的 `streamDiagram`，用 `CassetteSession` 回放模型调用，用 `onEvent` 收集事件。按发生先后报告第一处分歧：模型请求（JSON 路径）、事件（`events[k].data.…`，或事件名、payload 键顺序、事件相对模型调用的位置 `events[k].llm_calls`）、返回值（`result.result.…` / `result.error.…`）。报告写到 `reports/web_runs.json`。接口约定写在 `tools/parity-web.ts` 文件头：`streamDiagram(request, {chatModelFactory, onEvent, settings, engine, env, rendererUrl, resultsDir, signal})`。WP29 需要增加 fs / renderer 参数时，在这个文件里接上即可。
- **离线模式**：`--expected <dir> --actual <dir>` 比较两个已录好的用例目录；`--self-check` 让每个用例和自己比较。
- 比较规则：数值沿用 `compare.ts` 的容差；除 `result` 外，所有事件的 payload 键顺序都必须一致（前端解析的是 SSE 的 JSON 文本）；图片按第二期附录 C 的规则比较。`artifacts/` 只作为参考和人工查看用，不在 parity:web 里比较：生产默认会删除请求目录，而 TS 端在 MemoryFS 下也拿不到同样的目录。

## 偏差与发现（给 WP29）

1. **backend 流式出图只支持分步执行的 pipeline**。oneshot / unified 模式下，`begin_generation_run` 抛出 `RuntimeError("Stepwise generation currently supports pipeline mode only.")`，endpoint 把它映射成 `error {stage: "generation", message: "Diagram generation failed", detail: "The streaming generation request could not complete."}`。计划要求"多 agent / unified 两种模式"，录到的 backend 真实行为就是这个错误事件，浏览器版应当与之一致。backend 本身不提供切换 mode / critic 的入口，这两个参数是通过引擎端口注入的（见上文）。
2. 修复开启、校验开启且 critic 开启时，refiner 的 `prepare` 与校验**并行**执行（`asyncio.create_task`）。`prepare` 只做确定性工作，不调用模型，所以模型调用顺序是确定的。TS 侧可以串行执行，但结果必须一致。
3. `refining` 的 stage_start 用 `REFINER_TOTAL_STAGES`，stage_complete 用 `total_stages`，两者都是 9；`final_verification` 的 stage_index 是 8。final verification 失败时只有 stage_start、没有 stage_complete，随后是 `refine_error`、`refine_complete(failed)`。
4. 不覆盖 tldraw（"仅 Excalidraw 支持修复"的 `refine_complete` 分支），因为 tldraw 不在本期范围内。
5. 访客 / 登录用户的区别只体现在持久化和 DNA 上，本期都不迁移，所以只录了访客。
